## Why this is a `y` bump, and why that is honest

The rule is mechanical and lives in one place (`scripts/api-surface`, `next-version`): an added **or**
removed public line bumps `x` and resets `y`; no line at all leaves `x` and bumps `y`.

```text
$ dotnet scripts/api-surface/bin/Release/net10.0/picohex-api-surface.dll next-version --last v2026.11.0 --api-changed false --year 2026
2026.11.1

$ dotnet scripts/api-surface/bin/Release/net10.0/picohex-api-surface.dll next-version --last v2026.11.0 --api-changed true --year 2026
2026.12.0
```

`api-changed false` is the measured answer, not an assumption. The in-repo gate extracts every
packable surface from the current tree and diffs it against `api/`, which holds the surface of
`v2026.11.0`:

```text
$ bash scripts/check-api-baselines.sh report
=== surface delta since v2026.11.0: +0/-0 across 20 packable projects ===
the public API is unchanged, so the next release is a y bump: 2026.11.1
no surface drift: every baseline matches what the current tree extracts.
```

`32` commits landed between the two tags (`git rev-list --count v2026.11.0..main`; this notes commit
is the 33rd on the branch), and none of them touched a public signature. Two of them change what a
running process *does* under load, and a third changes what a sink may throw away. **`y` is a
statement about the surface, not about risk.** Here it is honest and it is also narrow: "`y`" means
"recompile nothing", not "notice nothing". The three behaviour changes below are the part of this
release a consumer can feel, and they are the part these notes exist to carry — a version number
shaped like a patch, inviting people to skip the notes, would be the dishonest version of this
release.

## Behaviour changes a consumer can feel

### 1. The six shutdown deadlines now hold when the `ThreadPool` is starved (`034480f`)

`v2026.11.0` recorded the defect as a limitation: `new CancellationTokenSource(TimeSpan)`,
`Task.WaitAsync(TimeSpan)` and `SemaphoreSlim.WaitAsync(TimeSpan)` enforce their budget with a
`Timer`, a timer callback is `ThreadPool` work, and under total starvation neither the cancel nor the
continuation behind it can be scheduled — so the wait did not end at all, and on a *partially* starved
pool it stretched without bound. **That limitation is superseded by this release**; the paragraph in
[`v2026.11.0.md`](v2026.11.0.md) is left exactly as published, because it is the record of what was
true at that tag.

One internal helper, four byte-identical copies (one per package — `PicoDI`, `PicoLog`, `PicoCfg` and
`PicoSchedule` share no assembly, and `PicoSchedule` has zero `PackageReference` by design), two
shapes:

- **blocking** — `ShutdownDeadline.WaitOrAbandon(Task|SemaphoreSlim, TimeSpan)`: the caller's own
  thread waits, bounded by a `Stopwatch`, so the thread that waits is the thread that times out. No
  worker has to be scheduled for the deadline to fire.
- **escalating** — `ShutdownDeadline.CancelAt(TimeSpan)` → `DeadlineSignal`: the cancel is performed by
  **one shared watchdog thread** per package, watching a `Stopwatch`, started by the first armed
  deadline and exited when none is outstanding (no thread per call, no thread while idle). The
  continuation behind `await task.WaitAsync(signal.Token)` is inlined onto that thread instead of being
  queued to a pool with no worker to give.

Applied to exactly the six shutdown call sites `v2026.11.0` enumerated:

| Site | `file:line` on `main` | Budget | Shape |
|---|---|---|---|
| PicoDI — per-hosted-service stop, used by `SvcContainer.DisposeAsync` and the failed-start rollback | `PicoDI/src/PicoDI/SvcContainer.Hosting.cs:447` | `HostedSvcStopTimeout`, 30 s (`:81`, internal) | escalating |
| PicoLog — drain budget of `LoggerFactory.DisposeAsync` | `PicoLog/src/PicoLog/CategoryPipeline.cs:137` | `LoggerFactoryOptions.ShutdownTimeout`, 30 s (`LoggerFactoryOptions.cs:39`); `TimeSpan.Zero` = unbounded, no deadline armed | escalating |
| PicoSchedule — tick-loop join in `StopAsync` | `PicoSchedule/src/PicoSchedule/Scheduler.cs:155` | `StopJoinBudget`, 5 s (`:37`, internal) | escalating |
| PicoSchedule — in-flight sink drain, its own budget | `PicoSchedule/src/PicoSchedule/Scheduler.cs:177` | `StopJoinBudget`, 5 s | escalating |
| PicoCfg — primary reload-gate wait in `CfgRoot.DisposeAsync` | `PicoCfg/src/PicoCfg/CfgRoot.cs:119` | 10 s (`:38`, internal ctor parameter) | blocking |
| PicoCfg — secondary gate drain attempt | `PicoCfg/src/PicoCfg/CfgRoot.cs:161` | 5 s (`:39`) | blocking |

**Measured before → after, 500 ms budgets.** The probes added with `034480f` occupy every
`ThreadPool` worker (`StarvedThreadPool.OccupyAll`,
`PicoLog/tests/PicoLog.Tests/StarvedThreadPool.cs`), then measure the deadline on a thread of their
own. The durations below are that run's TRX `duration` values on this machine, so each number includes
the probe's own setup:

| Probe | Measured |
|---|---|
| `PicoDI`: `CancelAt_UnderAStarvedPool_CancelsTheAwaitAtItsBudget` | **517 ms** |
| `PicoDI`: `BlockingWait_UnderAStarvedPool_StillEndsAtItsBudget` | **508 ms** |
| `PicoDI`: `SvcContainer_DisposeAsync_UnderAStarvedPool_AbandonsTheStopAtTheServiceBudget` | **504 ms** |
| `PicoLog`: `DisposeAsync_UnderAStarvedPool_CancelsTheInFlightSinkWriteAtTheDrainBudget` | **522 ms** |
| `PicoSchedule`: `StopAsync_UnderAStarvedPool_AbandonsTheTickLoopJoinAtItsBudget` | **514 ms** |
| `PicoCfg`: `BlockingSemaphoreWait_UnderAStarvedPool_EndsAtItsBudget` | **513 ms** |
| `PicoCfg`: `DisposeAsync_WithAStuckReload_UnderAStarvedPool_ReturnsAtItsTwoBudgets` | **1023 ms** (two budgets) |

i.e. **504–522 ms for a 500 ms budget**, and 1023 ms for the one site that spends two of them —
against a **never-returning** before. The before/after is recorded where the decision was made, not
only here: `PicoCfg/src/PicoCfg/ShutdownDeadline.cs:29` (`WaitAsync(token)` never returned;
`Wait(500 ms)` returned at 1.08x = 538 ms), `:41` (the same wait with the watchdog: 1.03x = 514 ms)
and `CfgRoot.cs:115` (1.18x = 590 ms for the `SemaphoreSlim` case); `v2026.11.0.md` measured the timer
spelling still waiting roughly 20x its budget on CI run 41813752088. With the mechanism reverted to the
timer shape the probes fail with "it returned never" — that is what they are for.

**What to do:** nothing, if your pool is not starved. Ordering, defaults, the `TimeoutException` an
abandoned phase produces and the failure reporting are all unchanged — the commit that made the change
lists each of them. If you were relying on a shutdown deadline firing *eventually* ("eventually" =
whenever a worker frees up), it now fires at the budget.

**What is still pool-dependent** — stated here, expanded under *Limitations still open*:

- the pipeline that runs **after** the drain is still pool work, so a starved pool can delay the last
  hop of `LoggerFactory.DisposeAsync`; what no longer needs a worker is the *cancellation*
  (`LoggerFactoryOptions.cs:36-37`, `PicoLog/README.md:383-389`);
- three of the four budgets are `internal` and cannot be retuned from outside
  (`HostedSvcStopTimeout`, `StopJoinBudget`, `CfgRoot`'s two ctor parameters); only
  `LoggerFactoryOptions.ShutdownTimeout` is public.

One detail a consumer cannot reach but should not be surprised by: `DeadlineSignal.IsExpired` is read
from the `Stopwatch`, so a **zero** budget reads expired before the work runs, where
`new CancellationTokenSource(TimeSpan.Zero)` cancelled on the timer's next tick and raced the check.
Only an internal test hook sets a zero budget.

### 2. `CfgRoot.DisposeAsync` may block its caller for up to 15 s instead of hanging forever (`034480f`)

`ICfgRoot : ICfg, IAsyncDisposable` (`PicoCfg/src/PicoCfg.Abs/ICfgRoot.cs:14`) is what
`CfgBuilder.BuildAsync` hands back (`api/PicoCfg.public.txt:44`), and `CfgRoot.DisposeAsync`
(`PicoCfg/src/PicoCfg/CfgRoot.cs:92`) waits for an in-flight reload before disposing providers. Those
two waits used to be `await _reloadGate.WaitAsync(timeout, CancellationToken.None)`; for a
`SemaphoreSlim`, **only the blocking spelling survives a starved pool** (measured in
`ShutdownDeadline.cs:28-29`: `WaitAsync(token)` never returned, `Wait(timeout)` returned at 1.08x the
budget), so this site takes the blocking shape in exchange for a bound it never had:

- **before** — the caller's thread returned immediately and the wait itself never ended under a
  starved pool: `DisposeAsync` hung, with no effective deadline at all;
- **now** — the calling thread does the timing, so the wait ends at the budget: **at most 10 s**
  (`CfgRoot.cs:119`) **plus at most 5 s** (`:161`) = **up to 15 s of synchronous block**, and only
  while a non-cooperative reload holds the gate. On a cooperative shutdown it is microseconds, exactly
  as before.

**What to do.** `await cfgRoot.DisposeAsync()` can now occupy the calling thread for up to 15 s in that
pathological case. Do not call it from a thread you are not allowed to block, and make your
`ICfgProvider.ReloadAsync` honour the `CancellationToken` it is given — a provider that does makes the
whole path immediate and this change invisible.

### 3. `SeqSink` drops the oldest entries past its cap instead of growing without bound (`00f8960`)

`MaxBatchEntries` (100, `PicoLog/src/PicoLog.Json/SeqSink.cs:22`) and `MaxBatchBytes` (256 KiB, `:25`)
are **trigger thresholds**: they start a drain, they never bounded the buffer, and the only appender
(`BufferEntries`) neither dropped nor refused. A flush tick that could not run — a starved pool, a
stalled HTTP call, both timer-shaped — therefore grew `_buffer` without bound: memory growth, and every
entry in it lost if the process exits. The cap is now explicit and drop-oldest, the policy the pipeline
queue already has:

| Constant | Value | `file:line` |
|---|---|---|
| `MaxBufferedEntries` | `MaxBatchEntries * 20` = **2000 entries**: the in-flight batch plus the 19 a stalled tick can leave queued behind it | `SeqSink.cs:39` |
| `MaxBufferedBytes` | `MaxBatchBytes * 20` = **5 MiB**, the same 20x factor so both dimensions trip together — a memory ceiling, not a delivery budget | `SeqSink.cs:48` |

`DropOldestPastTheCap` (`:260-279`, called from the appender at `:234`) removes from the head until the
buffer is inside both limits, and stops with **one entry still buffered**: an entry bigger than the
whole byte cap cannot be split, and refusing it would be a different policy. The trigger thresholds are
unchanged.

**What a caller observes.** Nothing on the write path — `WriteAsync` / `WriteBatchAsync` still
complete, never block and never throw — and on the wire the **oldest entries of the window simply never
arrive**. There is no public counter for it: the only "an entry was dropped" instrument,
`PicoLogMetrics.RecordDroppedEntry`, is `internal` to the `PicoLog` assembly this sink does not live
in, and the public counterpart (`RecordRejectedAfterShutdown`) means a different event. What exists is
the instance-scoped `DroppedByCap` test hook (`:100`) plus a `Trace` line (`:278`). Measured: 2500
entries buffered behind a stalled flush drop exactly **500**, the newest entry is in the sent batch and
the oldest is not (`SeqSinkBufferCapTests`, added with the commit).

**What to do.** Nothing to configure — there is no knob, on purpose; the cap is a memory ceiling. If
your Seq correlation assumes "every entry reaches the server", it does not any more: expect a hole at
the *start* of a stall window, not at its end. A sink whose write path applies backpressure
(`FileSink`) is the answer when losing an entry is unacceptable.

## What did NOT change

`api/` is byte-identical to the baselines `v2026.11.0` wrote — all **20** files, untouched:

```text
$ bash scripts/check-api-baselines.sh verify
reference release: v2026.11.0 (107f54c chore(release): v2026.11.0)
api/ matches v2026.11.0: no baseline differs from the release that wrote it.
The baselines still describe the last release; the current tree may have moved on.
```

(exit status **0**.) Concretely:

- **No public member was added, removed or reshaped** in any of the 20 packable packages. Both new
  types — `ShutdownDeadline` and `DeadlineSignal` — are `internal` in all four copies, and the
  `SeqSink` additions are `private`/`internal` constants and a private method.
- **The package set is unchanged**: still 20 packable projects, one baseline each, no new package and
  no new `PackageReference`. The helper uses `Thread`, `Monitor` and `Stopwatch` from the shared
  framework only, so `PicoSchedule` keeps its zero-dependency rule and `PicoLog` keeps
  `PicoLogCoreDeclaresNoSerializer` green.
- **The package *contents* did change, and it is not a surface change.** Each of the 20 now emits a
  `.snupkg` beside its `.nupkg` (`bd52383`, below), which no release before this one did. An extracted
  surface is identical with or without a symbol package, so `+0/-0` is the right answer for it — but a
  consumer gets something new (working source-stepping), and that belongs in the notes rather than in
  a delta that cannot see it.
- **No wire change.** `SeqSink`'s CLEF serialization is untouched; `00f8960` adds a drop loop in front
  of it. The 12 pinned wire shapes `v2026.11.0` changed are the same 12 after this release.
- **No exception contract change.** `Scheduler.StopAsync` still swallows its own deadline as a `Warn`
  log line (the `catch` moved from `TimeoutException` to `OperationCanceledException` filtered on
  `budget.IsExpired`, `Scheduler.cs:160-162` / `:182-184`), and `SvcContainer` still reports an
  abandoned phase as `TimeoutException`.

## Limitations still open

Updated, not copied: everything else in [`v2026.11.0.md`](v2026.11.0.md)'s own limitation list still
stands — that list is the record and is not repeated here. The item this release *does* supersede is
the pool-deadline one, and what replaces it is narrower than "fixed":

- **The post-drain pipeline is still pool work.** The deadline now reaches an in-flight sink write at
  the budget even with every worker occupied, but the rest of `LoggerFactory.DisposeAsync` needs a
  worker to finish, so a starved pool can still delay the last hop. Same after a `SvcContainer` stop
  phase and after `Scheduler.StopAsync`'s join. Said in the source (`LoggerFactoryOptions.cs:36-37`)
  and in the packed readme (`PicoLog/README.md:383-389`).
- **The four timer-shaped ticks are untouched**, on purpose — a late tick self-heals: `SeqSink`'s 2 s
  flush `PeriodicTimer` (`SeqSink.cs:157`, default at `:49`), `Scheduler`'s 10 s tick `Task.Delay`
  (`Scheduler.cs:691`, default at `Options.cs:71-72`), `FileWatchingCfg`'s 2 s watcher-retry `Timer`
  (`FileWatchingCfg.cs:160`, `WatchRetryIntervalMs` at `:49`) and its 200 ms debounce (`:200`, default
  at `:69`).
- **`SvcContainer` and `Scheduler` keep the escalating shape, and its pool-independence rests on one
  runtime property:** `CancellationTokenSource.Cancel()` runs the continuations waiting on that token
  **inline on the watchdog thread**. That is what lets an `await`-shaped `DisposeAsync` return at its
  budget without blocking the caller — but it is inlining, not a guarantee the BCL makes forever. The
  two `PicoCfg` sites do not rely on it (they block the calling thread). The cost of sharing one
  watchdog is head-of-line: a cancellation callback that blocks delays the deadlines behind it — the
  same hazard a `Timer` callback has today, minus the starved pool.
- **The `SeqSink` cap is silent on the public surface.** A dropped entry has no public counter; the
  only surviving evidence is an `internal` test hook and a `Trace` line. Making it public is a surface
  change, so it is not in a `y` release — and a consumer watching for loss has nothing to watch.
- **`BatchDispatchTests.BatchDispatch_SendsMultipleEntriesInOneCall` is a known flake.** It asserts
  `sink.BatchCallCount > 0` after three writes plus `FlushAsync`
  (`PicoLog/tests/PicoLog.Tests/BatchDispatchTests.cs:54`), so it fails whenever the pipeline delivers
  the three entries individually instead of batching them. Reproduced on this tree — i.e. on unmodified
  `main` plus these docs — as `Expected to be greater than 0 but received 0`, 1 of 202 in a run whose
  preceding run of the same binary was 202/0. **One other single-test failure happened once in five
  runs of this binary and was not captured** (the next run overwrote its report), and it did not
  recur in four consecutive re-runs of the same content — recorded here as unexplained rather than
  named as a second flake. Test-only, no product defect observed, nothing fixed here.
- **An empty symbol set does not fail the publish job.** `release.yml` errors when `packages` is
  empty but only *reports* the symbol count (`.github/workflows/release.yml:299-323`), so a release
  can ship 20 packages and 0 `.snupkg` and stay green — exactly the state that produced the
  `v2026.11.0` gap. The root cause is fixed (`bd52383`), not gated.
- **The analyzer tracking's rows are enforced by review, not by the build.**
  `_RequireAnalyzerReleasesFile` fails a build when a declared `AnalyzerReleases.*` file is missing,
  and that is the only machine-enforced half: `Microsoft.CodeAnalysis.Analyzers` arrives in these
  projects as a `build` asset only, so the release-tracking analyzer never loads and a deleted row or a
  flipped severity produces no diagnostic (`69cbacc`, `docs/releasing.md`).

## Tooling and process changes that matter to a release manager

None of these changes a package; all of them change how the next release is cut.

- **`api/` is CI-gated against the last release tag (`06ebb7a`).** New job `api-baselines`
  (`.github/workflows/ci.yml:215-241`: `ubuntu-latest`, 20 min, **no `needs`**, so it runs on every PR
  and push, `fetch-depth: 0` so the tags are in the clone). `scripts/check-api-baselines.sh verify` is
  the blocking step: `api/` must be byte-identical to `api/` at the newest release tag reachable from
  HEAD. That is a *drift detector*, not a "did the surface move" gate — development moves freely and
  `api/` deliberately lags `main` between releases, so the only way `api/` can differ from the tag is a
  hand-edit, which is the one action that corrupts the version decision (it makes the release tool
  answer `y` where an `x` is due). The `report` step is advisory by design
  (`if: ${{ !cancelled() }}`): green on a real surface change, red only when it cannot extract.
  Verification recorded by the commit: one line appended to `api/PicoLog.public.txt` → `::error::`,
  exit 1; restored → exit 0.
- **Symbols: both halves of the pipeline were broken, and fixing the obvious one alone changed
  nothing (`bd52383`, `1cc7535`, `4874cfb`).** `v2026.11.0` is the case study — it shipped 20
  packages and zero symbols.
  - **`pack` emitted no `.snupkg` at all** (`bd52383`). `IncludeSymbols` / `SymbolPackageFormat=snupkg`
    were declared in `Directory.Build.props` under `Condition="'$(IsPackable)' == 'true'"`, while
    `IsPackable` is defaulted to `false` earlier in that same file; properties evaluate in document
    order and the csproj body that sets it to `true` is read *after* `Directory.Build.props`, so the
    condition saw `false` for every project and the block never ran. Measured in the commit:
    `-getProperty:IncludeSymbols` answered empty and `-getProperty:SymbolPackageFormat` answered the
    NuGet default `symbols.nupkg`; packing `PicoDI.Abs` at `2026.11.0` into an empty directory left a
    lone `.nupkg`. The block now lives in `Directory.Build.targets` (`Directory.Build.targets:2-18`),
    which the SDK imports after the project body, where `IsPackable` is final — the same rule
    `AotOptimizationLevel` in that file already followed. Item groups were never affected (items are
    evaluated in a later pass), which is why the SourceLink/icon `ItemGroup` with the same condition
    did fire.
  - **The publish loop could not have pushed symbols that were never produced** (`1cc7535`). It
    iterated `*.nupkg` under a `[[ "$file" != *.snupkg ]]` guard — and `*.nupkg` never matches
    `.snupkg`, so that half of the guard was dead code. Packages and symbols are now collected into
    separate lists and pushed in two loops (`.github/workflows/release.yml:277-322`),
    `--skip-duplicate` on both; the remaining guard only fires for the legacy `*.symbols.nupkg`.
  - **`v2026.11.0` stays symbol-less unless someone dispatches the repair** (`4874cfb`,
    `.github/workflows/backfill-symbols.yml`). It published 20 packages and **zero** symbol packages
    (`gh release view v2026.11.0 --json assets` → 20 assets, 0 of them symbols), and a NuGet version is
    immutable, so the only way to complete that release is to push the `.snupkg` files afterwards at
    the version already on the feed. The workflow is `workflow_dispatch`-only with a `tag` input
    defaulting to `v2026.11.0`, checks the tag out and proves `HEAD` is it, re-packs the same 20
    projects in the same three phases as `release.yml`'s `pack` job, pushes **only** `.snupkg` files
    with `--skip-duplicate`, and fails on a `.nupkg`, a foreign version or an empty set. It is
    deliberately not a branch of `release.yml`: that path is production-validated and a regression
    there costs a release. **It has not been run** — nothing in this repository can verify a push to
    nuget.org, so a consumer of `2026.11.0` gets source-stepping only once it is.
- **The rest of `release.yml` (`1cc7535`, `4e8061b`).**
  - `pack` declares `outputs.version`, which `publish.name` reads, instead of silently falling back to
    `github.ref_name`.
  - `upload-artifact@v7` / `download-artifact@v8` are paired on purpose (both node24,
    protocol-matched); do not bump one alone (`.github/workflows/release.yml:217`, `:262`).
  - **The notes file is a hard input.** A `notes` step resolves
    `docs/release-notes/${GITHUB_REF_NAME}.md` and exits 1 with `::error::` when it is missing or empty
    (`.github/workflows/release.yml:325-348`); the file becomes the release body via `body_path`, with
    the generated compare link appended (`:355-359`). It warns above 120000 bytes, because GitHub
    truncates the body at 125000 silently. **Mind the order:** the step sits *after* both NuGet push
    loops (`:275` → `:325`), so a missing notes file fails the run **after** the packages are already
    on nuget.org — the version is spent and the tag is immutable. Write the file before tagging; this
    file is that file for `v2026.11.1`.
  - `pack`'s artifact upload gained `if-no-files-found: error` (`:232`), so a pack step that produced
    nothing can no longer stay green and surface one job later in `publish`.
- **Analyzer release tracking exists, and this release promotes nothing (`b5caf5b`, `0a52b39`,
  `69cbacc`, `4e8061b`, `2cde46c`).** `AnalyzerReleases.Unshipped.md` + `AnalyzerReleases.Shipped.md`
  in the four generators that declare rules — `PicoAop.Gen` 7, `PicoCfg.Gen` 10, `PicoDI.Gen` 5,
  `PicoMediator.Gen` 1 = **23 rule IDs** (`PicoLog.Gen` declares none, so it has neither file) — with
  `RS2008` dropped from all five `NoWarn`s, and `_RequireAnalyzerReleasesFile` failing a build when a
  declared file is missing. Those rules reach consumers inside the `*.Abs` packages
  (`analyzers/dotnet/cs`), all 23 `isEnabledByDefault: true` (18 `Error`, 5 `Warning`).
  **The `Shipped.md` rows are back-dated, not promoted:** 14 first shipped in `v2026.1.1`, 4 in
  `v2026.1.2`, 1 in `v2026.8.1`, 1 in `v2026.8.6` and 3 (`PICO111`/`112`/`113`) in `v2026.11.0` — 5
  tags, measured with one `git grep` per ID per tag plus a check that the tag published a package
  carrying the generator. Promoting all 23 under one tag would have been false for 20 of them. **This
  is a record change, not a behaviour change**, and it is why `docs/releasing.md` now carries the
  promotion rule ("promote at the release, in the same commit that writes
  `docs/release-notes/<tag>.md`", `docs/releasing.md:55-58`). Applied to `2026.11.1`: **nothing to
  promote** — both tables in all four `Unshipped.md` files hold no rows and no descriptor was added,
  reworded or retired, so no `## Release 2026.11.1` section was written; an empty one would claim rules
  first shipped here.
- **Documentation that now matches the packages (`2839e8d`, `4e8061b`, `970adb7`, `2cde46c`).** The
  root module table and `PicoAop/README.md`'s Packages table now list the packages the csprojs actually
  pack — the six rows sum to **20**, equal to `api/*.public.txt` and to an `IsPackable=true` scan of
  the 20 `src/` csprojs; `PicoSchedule/README.md` gained its missing `## Packages` section;
  `docs/releasing.md` documents the notes-and-symbols contract above.
- **Dependencies, all on the latest stable (`041def2`, `11fd7ba`).** `PicoJetson` / `PicoYaml` /
  `PicoIni` / `PicoToml` **2026.13.0 → 2026.13.3** in two hops (`.13.1` in `041def2`, `.13.3` in
  `11fd7ba`); `TUnit` **1.65.51 → 1.83.8**;
  `Microsoft.Extensions.{Configuration,DependencyInjection,Logging,Logging.Console}` and
  `Microsoft.Bcl.AsyncInterfaces` **10.0.11 → 11.0.0**; `Microsoft.SourceLink.GitHub`
  **10.0.400 → 11.0.100**; the testing `HangDump`/`CrashDump` extensions **2.3.3 → 2.5.3**;
  `PicoBench` **2026.2.6 → 2026.4.0** (`Directory.Packages.props`). No code adaptation was warranted or
