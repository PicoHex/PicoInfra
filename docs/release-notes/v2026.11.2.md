## Why this is a `y` bump, and why that is honest

The rule is mechanical and lives in one place (`scripts/api-surface`, `next-version`): an added **or**
removed public line bumps `x` and resets `y`; no line at all leaves `x` and bumps `y`.

```text
$ dotnet scripts/api-surface/bin/Release/net10.0/picohex-api-surface.dll next-version --last v2026.11.1 --api-changed false --year 2026
2026.11.2

$ dotnet scripts/api-surface/bin/Release/net10.0/picohex-api-surface.dll next-version --last v2026.11.1 --api-changed true --year 2026
2026.12.0
```

`api-changed false` is measured, and **measured twice by two tools that share no code path** — the
skill's own release tool and the repository's gate:

```text
$ pwsh -File .../picohex-skills/skills/picohex-release/scripts/release.ps1 -RepoRoot <tree> -DryRun
...

```

`8` commits landed between the two tags (`git rev-list --count v2026.11.1..main`; this notes commit is
the 9th on the branch), and none of them touched a public signature. **`y` is a statement about the
surface, not about what a consumer installs.** Here that gap is wider than usual and it is the whole
point of this release:

- **Nothing a consumer *compiles against* moves.** Every type, member, parameter name, default and
  attribute on it is the line-for-line same set as `v2026.11.1` — and after this release it is the same
  set **in both assemblies**, which the section below measures rather than asserts.
- **What a consumer *resolves* does move.** A project targeting `net11.0` used to fall back to the
  `net10.0` asset (nearest-compatible); it now gets a `net11.0` asset. A project on `net10.0` — or on
  anything older, or `netstandard2.0` — resolves exactly the assembly it resolved before, unchanged.
- **What a consumer must have *installed* to consume them does not move.** Nothing about .NET 11 is
  required to *use* these packages; only building this repository now requires an SDK that can target
  `net11.0`.

So `y` is honest and it is narrow: "recompile nothing", not "nothing to read". A version number shaped
like a patch, inviting people to skip the notes, would be the dishonest version of this release — the
package they install is not the package they installed last week.

## The headline: every project multi-targets `net10.0` and `net11.0` (`c7daf87`)

`112` files in one commit: `53` csproj, `52` `packages.lock.json`, `Directory.Build.props`,
`Directory.Build.targets`, `4` workflows and `global.json` — the lock files among them have since been
untracked, which is the change the *Dependency policy* section below ends on.

### Which projects, which frameworks

Measured on `main` (`c7daf87`), not from the commit message:

```text
$ grep -rn --include=*.csproj '<TargetFrameworks>' . | wc -l
53
$ grep -rn --include=*.csproj '<TargetFramework>' . | wc -l
5
$ find . -name '*.csproj' | wc -l
58
```

`58 = 53 + 5`: every project is one or the other, with no exceptions and no third shape.

| Projects | TFM(s) | Count | What it covers |
|---|---|---|---|
| Multi-targeted | **`net10.0;net11.0`** | **53** | All 20 packable projects, all 15 test and compile-gate projects, all samples, all benchmarks, and `scripts/api-surface` |
| Single-targeted | **`netstandard2.0`** | **5** | `PicoAop.Gen`, `PicoCfg.Gen`, `PicoDI.Gen`, `PicoLog.Gen`, `PicoMediator.Gen` — the Roslyn source generators, whose TFM is set by the compiler host's loader, not by us |

The five that stay behind are the ones that **must**: a Roslyn analyzer is loaded by `csc`, so its
assembly has to be loadable by every SDK that compiles a consumer's project. Their lock files still
carry one section, and it is named for that framework — `".NETStandard,Version=v2.0"` — not for a
`net*` TFM.

resolves, and whatever it resolves at pack time is what that release pins for consumers.

### What a consumer needs

- **To build against `lib/net10.0`:** nothing new. Same SDK, same runtime, same code.
- **To build against `lib/net11.0`:** an SDK that can target `net11.0` (and, to run it, the .NET 11
  runtime). Choosing the asset is NuGet's job: it picks the `lib/` folder nearest the project's TFM, so
  `net10.0` and older keep the `net10.0` assembly, `net11.0` gets the `net11.0` one, and a future
  `net12.0` project gets the `net11.0` one as nearest.
- **Native AOT on `net11.0` works, and was proven.** The lock files resolve the AOT toolchain **per
  TFM** — `Microsoft.DotNet.ILCompiler` and `Microsoft.NET.ILLink.Tasks` at **10.0.15** for `net10.0`
  and **11.0.0** for `net11.0` (`PicoLog/src/PicoLog/packages.lock.json`) — so the two legs do not
  share one compiler package. Published and ran for real:

$ ./PicoSchedule.Sample.exe

### What the change forces on every framework-specific command

Adding a second TFM changes what a *TFM-less* command means: anything that has to pick exactly one
framework now has to be told which. Two failures, both measured on this tree:

```text
# 1. an SDK that cannot target net11.0 - the whole build now fails, not "the net11.0 half"
$ # global.json pinned to sdk 10.0.404
$ dotnet build PicoSchedule/src/PicoSchedule/PicoSchedule.csproj -c Release
error NETSDK1045: The current .NET SDK does not support targeting .NET 11.0.
  ... [PicoSchedule.csproj::TargetFramework=net11.0]

# 2. an operation that needs a single framework
$ dotnet publish PicoSchedule/src/PicoSchedule/PicoSchedule.csproj -c Release
error NETSDK1129: The 'Publish' target is not supported without specifying a target framework.
  The current project targets multiple frameworks, you must specify one of the following
  frameworks in order to publish: net10.0, net11.0
```

Both are load-bearing for the release, so both were fixed at the source rather than documented away:

- **`global.json` no longer pins an SDK.** `c7daf87` deletes the whole `sdk` block (it pinned
  `10.0.400` with `rollForward: latestFeature`), and what remains is
  `{"test": {"runner": "Microsoft.Testing.Platform"}}`. Consequence — and it is a limitation, listed
  below: a machine with only the .NET 10 SDK gets `NETSDK1045` from inside a build instead of a clear
  "SDK too old" from the resolver. Every workflow moved to `DOTNET_VERSION: 11.0.x` (`ci.yml:23`,
  `release.yml:17`, `backfill-symbols.yml:33` — the fourth, `deps-refresh.yml`, no longer exists), so CI
  is unambiguous; a laptop is on its own.
- **`-f` is added everywhere a single framework is required.** `Directory.Build.targets`'s
  `PublishAotIfRequested` passes `-f $(TargetFramework)` into the nested `dotnet publish` — and the
  comment there records why it is not cosmetic: that `Exec` starts a **new** msbuild process which
  re-evaluates the project from scratch and inherits nothing about the framework the `Run` was invoked
  for. `ci.yml` gained `-f net10.0` on all six AOT publish validation steps and on the three managed
  sample runs (`:335`, `:339`, `:343`, `:494`, `:694`, `:698`, `:825`, `:958`, `:1089`).
- **The repository's own documentation was pinned the same way, because that is where a contributor meets
  it.** `2249f74` adds `-f net10.0` to all six TFM-less command examples in three files:
  `CONTRIBUTING.md:83` and `:142` (a managed `dotnet run` of a test project, and a `dotnet publish` with
  AOT), `PicoLog/benchmarks/PicoLog.Benchmarks/README.md:8,10,12` (the three benchmark invocations) and
  `README.md:527` (the benchmark example). Docs only — no code, no workflow, no csproj, no surface — and
  every one of them says `net10.0`, the leg a contributor can run without the .NET 11 runtime installed.

**What to do:** if you build this repository, install the .NET 11 SDK. If a script of yours publishes
or runs a project from it, pass `-f net10.0` (or `net11.0`) — it is now mandatory, and the error is
`NETSDK1129`.

## Dependency policy: float the fix segment, record the resolution locally (`ed6a3f4`, `c862d2c`, `c28d33b`)

Five commits — `ed6a3f4`, the two CI changes `9e23868` / `0d23ef4`, the merge `c862d2c` (parents
`81ed4bb` + `0d23ef4`) and `c28d33b`, which keeps the float and the watch and drops the committed record.
None of them changes a shipped assembly; all of them change what a build resolves and what a release
manager must do.

### One float rule, applied to every declaration

`Directory.Packages.props` floats **only the segment the publisher promises will not break** — the last
one:

| Tier | Shape | Example |
|---|---|---|
| First-party `Pico*` | `<year>.<x>.*` | `PicoJetson` **`2026.13.3` → `2026.13.*`**, likewise `PicoYaml` / `PicoIni` / `PicoToml` |
| Third-party | `<x>.<y>.*` | `TUnit` **`1.83.8` → `1.83.*`**, `Microsoft.Testing.Extensions.{HangDump,CrashDump}` **`2.5.3` → `2.5.*`**, `Microsoft.CodeAnalysis.CSharp` **`5.9.0` → `5.9.*`** |
| `Microsoft.Extensions.*`, `Microsoft.SourceLink.GitHub`, `Microsoft.Bcl.AsyncInterfaces`, `PicoBench` | `<x>.<y>.*` | `11.0.0` → `11.0.*`, `11.0.100` → `11.0.*`, `2026.4.0` → `2026.4.*` |
| The 18 packages this repo publishes | `$(Version)` | exempt — the release pipeline owns that number |

Floating under Central Package Management is not free: NuGet rejects it with **NU1011** unless
`CentralPackageFloatingVersionsEnabled` is `true`, so that switch is part of the rule and `ed6a3f4` adds
it (`Directory.Packages.props:19`) next to the `CentralPackageTransitivePinningEnabled` that makes the
central float govern *transitive* resolution too, not just the projects that name the package directly.

### Lock files: float the declarations, record the resolution locally, ship it as a CI artifact

`ed6a3f4` deleted the second half of the lock-file condition — the one that excluded `samples`,
`benchmarks` and `scripts` — and deleted its cause in the same commit.
`UseDefaultPublishRuntimeIdentifier=false` stops the SDK from inferring the *host* RID for an AOT
executable, which is what used to write a machine-specific `"net10.0/win-x64"` section into those
projects' lock files. With that cause gone the exclusion had nothing left to protect, so **every project
in the solution writes a record**. `c28d33b` then decided what that record is: not a pin — it never was
one, because the declarations float — but a **local, ignored record of what one restore resolved**,
shipped as CI data instead of committed as a file. Four things, and none of them a tracked file:

| | Where | What it does today |
|---|---|---|
| **float** | `Directory.Packages.props` | the **declarations** — which safe range each package may move inside |
| **record** | restore, beside each project | `RestorePackagesWithLockFile` stays **`true`** (`Directory.Build.props:151`): it is the switch that *writes* the record, and turning it off would leave nothing to inspect — the opposite of the intent. Untracked is not off |
| **ignore** | `.gitignore:64` | a bare `packages.lock.json` pattern, which git applies at every level — `git check-ignore -v src/probe/packages.lock.json` matches it too |
| **artifact** | `ci.yml` | each of the six validating jobs uploads `**/packages.lock.json` as `resolved-versions-<area>-<rid>`, `if: always()`, 30 days — the one job the tracked lock used to do |

Both halves measured on this tree:

```text
$ git ls-files '*packages.lock.json' | wc -l
0

$ find . -name packages.lock.json | wc -l
58

$ git check-ignore -v PicoLog/src/PicoLog/packages.lock.json
.gitignore:64:packages.lock.json	PicoLog/src/PicoLog/packages.lock.json
```

`58` records exist on disk and none is in the tree: the 57 that were tracked until `c28d33b` were
`git rm --cached`'d rather than deleted, and `scripts/api-surface` never was tracked. `git status` cannot
see any of them — which retires the release-tree failure the old design kept producing, because
`dotnet publish` writes RID-specific entries (`Microsoft.DotNet.ILCompiler`) into the lock beside the
project and that used to dirty the tree on every release.

**The record's shape did not change, only its home.** Sections per file over all 58 on disk:

```text
$ # dependency sections per packages.lock.json on disk
      5 .NETStandard,Version=v2.0
     53 net10.0,net11.0
```

`53 = 52 + 1` — the 52 multi-targeted projects in `PicoInfra.slnx`, plus `scripts/api-surface`, which is
not in the solution and has a record only where somebody built it; and `5` is the `netstandard2.0`
generators. So a multi-targeted project still gets exactly two dependency sections, `"net10.0"` and
`"net11.0"`, and a source generator exactly one `.NETStandard` section. Verified by writing them rather
than by reading them:

```text
$ dotnet restore PicoLog/src/PicoLog/PicoLog.csproj -p:UseProjectReferences=true --force-evaluate
  Restored .../PicoLog.csproj
  # sections: net10.0, net11.0

$ dotnet restore PicoLog/src/PicoLog.Gen/PicoLog.Gen.csproj --force-evaluate
  Restored .../PicoLog.Gen.csproj
  # sections: .NETStandard,Version=v2.0
```

The `UseProjectReferences == 'true'` condition is still there, still load-bearing, for the other half of
what it always said: the switch rewrites a sibling `PackageReference` into a `ProjectReference`, so the two
modes resolve two genuinely different graphs and one record cannot describe both — the record covers the
inner-loop / CI graph, the only one that restores in a plain checkout. What `c28d33b` deleted is the
sentence that read the record as an invariant (`Invariant: a multi-targeted project's committed
packages.lock.json has exactly two dependency sections …`, in `Directory.Build.props` before that commit).
The fact survives; the enforcement does not, because a file nobody commits cannot be enforced.

**What CI does instead of locking.** The 13 per-project `dotnet restore` commands no longer carry
`-p:RestoreLockedMode=true` (`ci.yml:291`, `:425-431`, `:621-622`, `:792`, `:928`, `:1061`;
`grep -c RestoreLockedMode .github/workflows/ci.yml` → `0`). A locked restore means "restore only from the
committed record", and nothing is committed — it would have no subject, and kept in place it would red
every leg the first time a patch moved inside its band, punishing exactly the behaviour the float exists to
allow. Each of those six jobs uploads the record it produced instead, which answers "which versions did
that build use" for a green run *and* for a red one.

**What a contributor must do when a package moves.** Two edits, one of them to a file:

```shell
# 1. move the band (or the version) in Directory.Packages.props
# 2. re-resolve - restore writes the new record; there is nothing to commit but the props
dotnet restore PicoInfra.slnx
# 3. only if this machine already holds a record from before the move
dotnet restore PicoInfra.slnx --force-evaluate
```

Step 3 is the one that catches people, for the opposite reason it used to: a plain restore **reads** an
existing record, so a machine that restored before the move stays on the old patch while a fresh CI runner
is already on the new one — that is the record working, not a bug, and `--force-evaluate` is how you
re-shoot it. Step 2 also ends differently: nothing goes into `git add`, `git status` stays clean, and the
only tracked file a version bump touches is `Directory.Packages.props`. The cost is stated plainly by the
commit and repeats here — two machines restoring the same commit can resolve different patches inside the
band, and the repository no longer records which; the per-build `resolved-versions` artifact is where that
answer lives. Nothing in `CONTRIBUTING.md` or `docs/releasing.md` says any of this yet, and the job header
that used to carry it (`deps-refresh.yml`) is gone: the rule now lives in `Directory.Build.props:120-149`,
in the comment block above `.gitignore:64`, and above each upload step in `ci.yml`. That gap is recorded
under *Not shipped with this release*.

### When the float moves, and when a person must

The float resolves a patch on its own; it can never leave its band. `c28d33b` then deleted the job that
turned a patch into a diff, which leaves one mechanism and one detector:

| Job | Trigger | What it answers | Can it write? |
|---|---|---|---|
| `upstream-watch.yml` (`9e23868`, 240 new lines; `c28d33b` reworded its header to say what a lock file now is) | **`workflow_dispatch` only** | "which band has upstream *left*?" — asks nuget.org's flat-container index for the latest stable of every `<PackageVersion>`, compares the declared band, and writes a job-summary table plus one issue updated in place | **no** — `permissions: contents: read`, and its header says it must never edit props, locks or versions |

`deps-refresh.yml` is **gone** — 107 lines, `c28d33b`. Its entire product was a PR whose diff was lock
files; with the record untracked that PR can only ever report "no change", and with nothing locked a plain
`dotnet restore` already floats to the newest version inside the band by itself. Nothing replaced it in the
pipeline, because nothing needs to: the float *is* the mechanism now, and `0d23ef4`'s on-demand trigger
disappears with the job it triggered.

What still needs a person is the other half, and the reason is not cosmetic: a restore re-resolves
**inside** each declared range and never outside it — `2026.13.*` can never resolve `2026.14.0` — so
neither the float nor the `resolved-versions` artifact can report that a band moved. `upstream-watch` is
that missing detector, and it was made on-demand for the same reason the refresh was: a band moves before
a release, when the next version is being chosen anyway, and a red run on a calendar would only teach
everyone to ignore it. It never fails the build for a migration being due.

**The pre-release step this creates:** dispatch `upstream-watch` before choosing a version — one job, not
two. `docs/releasing.md` does not mention it yet (see *Not shipped with this release*).

## Limitations still open

Carried forward from [`v2026.11.1.md`](v2026.11.1.md) — what still holds, and nothing more; that file is
the record and its own list is not repeated here.

- **The post-drain pipeline is still pool work.** The shutdown deadline reaches an in-flight sink write
  at its budget even with every `ThreadPool` worker occupied, but the rest of
  `LoggerFactory.DisposeAsync` needs a worker to finish, so a starved pool can still delay the last hop.
  Same after a `SvcContainer` stop phase and after `Scheduler.StopAsync`'s join
  (`LoggerFactoryOptions.cs:36-37`, `PicoLog/README.md:383-389`). Untouched by this release.
- **The four timer-shaped ticks are untouched**, on purpose — a late tick self-heals: `SeqSink`'s 2 s
  flush `PeriodicTimer` (`SeqSink.cs:157`, default at `:49`), `Scheduler`'s 10 s tick `Task.Delay`
  (`Scheduler.cs:691`, default at `Options.cs:71-72`), `FileWatchingCfg`'s 2 s watcher-retry `Timer`
  (`FileWatchingCfg.cs:160`, `WatchRetryIntervalMs` at `:49`) and its 200 ms debounce (`:200`, default
  at `:69`). Untouched by this release.
- **`BatchDispatchTests.BatchDispatch_SendsMultipleEntriesInOneCall` is still a known flake.** It
  asserts `sink.BatchCallCount > 0` after three writes plus `FlushAsync`
  (`PicoLog/tests/PicoLog.Tests/BatchDispatchTests.cs:54`), so it fails whenever the pipeline delivers
  the three entries individually instead of batching them. Not observed in this release's
  `PicoLog.Tests` run (404/0), and not fixed — the flake is a test-shape problem, not a product defect,
  and fixing it is not a `y`-release change.
- **The `SeqSink` cap is still silent on the public surface**, the escalating shutdown shape still rests
  on `CancellationTokenSource.Cancel()` running continuations inline on the watchdog thread, an **empty
  symbol set still does not fail** the publish job (`release.yml:299-323` reports the count, it does not
  gate it), and the `AnalyzerReleases.*` rows are still enforced by review rather than by the build
  (that analyzer arrives as a `build` asset only). All four are `v2026.11.1` findings, re-read against
  this tree and still true.

Added by this release:

- **Building this repository now requires an SDK that can target `net11.0`, and `global.json` no longer
  says so.** `c7daf87` deletes the `sdk` block that pinned `10.0.400`; the remaining `global.json`
  carries only `test.runner`. On a machine with the .NET 10 SDK only, any build of a multi-targeted
  project fails with `NETSDK1045` naming `net11.0` (measured above) — mid-build, per project, rather
  than once, up front. Every workflow is on `DOTNET_VERSION: 11.0.x`; nothing in the repository checks
  a contributor's SDK before the first `dotnet build`.
- **Every framework-specific command needs an explicit `-f`.** `dotnet publish`, `dotnet run` and any
  `-t:Publish` / `-t:Run` on a project from this repository now fail with `NETSDK1129` unless one
  framework is named (measured above). `ci.yml` and `Directory.Build.targets` were fixed, the six command
  examples in the repository's own docs were fixed in `2249f74`, and `release.yml` needed nothing — it
  only packs and tests, and both are TFM-agnostic. A consumer's own script that shells out to this tree
  is not covered by anything here.
- **`check-api-baselines.sh report` now compares one TFM, and which one is arbitrary.**
  `find_assembly` picks the newest `bin/Release/**/{AssemblyName}.dll` by mtime
  (`scripts/check-api-baselines.sh`), and both legs are written in the same instant — measured
  `-printf '%T@'` values identical to the tick for `net10.0` and `net11.0`. So the `+0/-0` verdict is
  one leg's, not both. It is harmless *today* only because the two surfaces are identical for all 20
  packages, which is why this release verified them separately; a future change that compiles
  differently per TFM would make the gate's answer depend on file timestamps. The same shape exists in
  the release tool's `Get-Surface`: it computes the first TFM from `<TargetFrameworks>` and then selects
  the assembly by `LastWriteTime` instead.
- **An explicit `-r` still writes RID-shaped sections into the record — now two of them — and that is what
  the ignore line is for.** `UseDefaultPublishRuntimeIdentifier=false` only suppresses the SDK's
  *implicit* RID. A `dotnet publish -r win-x64 -p:PublishAot=true` (the spelling in `ci.yml` and in
  `CONTRIBUTING.md:142`) adds `"net10.0/win-x64"` **and** `"net11.0/win-x64"` sections to the project's
  `packages.lock.json` — measured on `PicoSchedule/samples/PicoSchedule.Sample`, restored afterwards.
  Under the old design that was a dirty tree a contributor had to `git checkout` before releasing; since
  `c28d33b` the file is ignored, so the publish leaves `git status` untouched and the RID-shaped record
  stays a local fact. One residue survives the change: a later plain restore on that machine *reads* the
  record, so `dotnet restore --force-evaluate` is how you put it back on the host-neutral graph.
- **Three shipped READMEs still describe a single framework, and they ship inside the packages.** All 20
  `.nupkg` files carry a `README.md`; after this release three of them are wrong about the TFM:
  `PicoLog/README.md:478,479,481,482` (a `| net10.0 |` Packages column), `PicoSchedule/README.md:91,93`
  ("One package at `net10.0`") and `PicoMediator/README.md:6-8` ("`PicoMediator.Abs` targets
  `net10.0`"). `README.md:504` (repository root, not packed) has the same shape. Recorded rather than
  fixed here: this commit is the notes file only, and a README edit belongs with the code that caused
  it.
- **`scripts/api-surface`'s lock file used to be the one thing that made `git status` dirty after a
  build, and `c28d33b` cleared it as a side effect.** `RestorePackagesWithLockFile` is set for every
  project under the repository when `UseProjectReferences` is on, so building the extractor leaves
  `scripts/api-surface/packages.lock.json` behind. Until `c28d33b` it was untracked and *not* ignored, so
  the release path — it refuses a tree with anything in `git status --porcelain`
  (`scripts/release.ps1:52-54`) — saw it, and every freshly built checkout had to be cleaned by hand. The
  ignore line covers it like every other record now, and a built tree reports clean.
