## Why this is an `x` bump and not a `y` bump

`2026.10.1` → `2026.11.0`: the public API changed, even though most of the change is additive. The
rule is "API changed", not "API broke" — one added public member bumps `x`, and `y` returns to `0`.
The tool answers this directly:

```text
$ dotnet picohex-api-surface.dll next-version --last v2026.10.1 --api-changed true --year 2026
2026.11.0
```

(`api/*.public.txt` at `main` commit `24c72c5`, the release-prep commit that seeds them; the copies I
measured against, taken from `chore/release-prep` at `356d504`, are byte-identical to them):

`PicoLog.Json`, `PicoSchedule` — the same six packages and the same per-package counts this release

## Wire and behaviour deltas (surface identical, behaviour is not)

The API diff cannot see any of the items in this section. Each one changes what a consumer
observes, so they are stated here rather than inferred from silence.

### `PicoLog.Json` — the SeqSink wire bytes changed spelling (`994534d`)

`SeqSink` now builds each CLEF batch with the PicoJetson `JsonWriter` instead of the hand-rolled
escaper it carried while it lived in the core package. Same document, same content type
(`application/json; charset=utf-8`), same envelope recreated per retry — but **5 of 12 pinned wire
shapes differ in how a character is spelled**:

- `\b` and `\f` are emitted as `\u0008` and `\u000C` (the writer only uses the short form for the
  three escapes JSON defines: `\n`, `\r`, `\t`);
- hex digits are uppercase (`\u001F`, not `\u001f`);
- an unpaired surrogate reaches the wire as the UTF-8 bytes of U+FFFD (3 bytes) instead of the
  escape text `\ufffd` (6 bytes) — the same substitution the old code chose deliberately.

All 12 shapes decode to the identical document, and the bytes are now pinned by
`SeqSinkWireFormatTests`. A Seq server sees no semantic difference; a byte-for-byte snapshot on
your side will.

### `PicoCfg` — TOML and YAML are parsed by their format's reader (`edf2cfd`, `79b3283`, `660bb30`)

The two text backends used to carry a hand-written line splitter each. They now read through
`TomlReader` / `YamlReader`, which changes what a *given* document flattens to:

| Document | Before | Now |
|---|---|---|
| `Servers:` + `- a` + `- b` | the sequence vanished (a `- a` line has no `:`) | an array; skipped unless `flattenArrays: true` |
| `Script:` + a block scalar body | `Script` held the indicator character, body vanished | block scalar read as one value |
| `Items:` + `- name: x` | everything vanished | an array of tables |
| `[[servers]]` + `name="alpha"` | key `[servers]:name`, every row but the last silently overwritten | `servers:0:name`, one row per element |
| `ports = [1, 2, 3]` | the literal string `"[1, 2, 3]"` | an array; skipped unless `flattenArrays: true` |
| `[[s]]` … `[z]` after it | `z`'s keys landed under `s:0:` | each key under its own table |
| `host = "h"` + `ports = [1, 2]` | `ports == "h"`, elements at the root as `0`/`1` | `ports:0`, `ports:1` |

A configuration that loaded on `2026.10.1` can therefore resolve to **different values**, or to the
same values under different keys, without any compile error. `PicoCfg.Ini` is deliberately
unchanged (INI has no arrays) and `PicoCfg.Json` was already the counter-example.

These three commits are **not** in [`CHANGELOG.md`](../../CHANGELOG.md). That is a gap, not a scope
decision: the CHANGELOG already carries six behaviour-only PicoDI entries, so a behaviour break of
this size belongs there too, and a CHANGELOG kept in step with the API diff will keep missing
them. They are recorded here instead, which is currently the only place that describes them. The
CHANGELOG edit made with this release is deliberately limited to the one undocumented delta line
(see the cross-check below), so these three entries are still owed.

### `PicoCfg` — the collision guard also changes an INI *rule* (`da73005`)

Declared in the CHANGELOG (cross-referenced below, not repeated): `':'` may no longer appear in an
INI section name or key, because INI already nests with `'.'`. This is a new document rejection,
not a new member.

Four items break someone. Three appear in the API delta — two as removed lines, one as the new
exception type — and one, the TOML/YAML parser swap, is a semantic change the delta cannot see.
Seven further behaviour breaks ship in this version and are already declared in
[`CHANGELOG.md`](../../CHANGELOG.md) — cross-referenced below, not repeated.

| # | Change | Kind | Migration |
|---|---|---|---|
| 1 | `PicoLog.SeqSink` moved to the `PicoLog.Json` package | source + binary | `dotnet add package PicoLog.Json`; `using PicoLog;` and `new SeqSink(...)` compile unchanged. ## Limitations left open

Product limitations, unchanged and unhidden:

- **YAML reader gap, compensated nowhere on purpose.** YamlReader delivers the first inline member
  of a sequence item (`- name: x`) as one raw string, and a nested sequence (`- - 1`) as `"- 1"`.
  Splitting those here would put a hand-written YAML parser back in the flattener — the bug that
  was just removed. `YamlNestedStructureTests` pins what the reader actually delivers.
- **TOML inline tables** (`t = { a = 1 }`) still flatten `a`/`b` without the `t` prefix.
- **Nested value arrays** (`m = [[1, 2], [3]]`) still collide at `m:0`.
- **`PicoCfg.Json` is not covered by the collision guard** — it flattens the same way and stays
  last-wins.
- **No `SeqSink` forwarder, no `[Obsolete]` stub** — a forwarder would make `PicoLog.dll` reference
  `PicoLog.Json.dll` and through it the serializer; a stub would keep the JSON-writing code in core.
- **`flattenArrays` is undocumented in prose.** It has XML docs on all four methods and has been
  on `AddJson` since `2026.10.1`, but no tracked Markdown file mentions the name at all
  (`grep -rn flattenArrays --include=*.md` → none) — not the JSON switch either. Worth a sentence
  in `PicoCfg/README.md` next release.

### Tool blind spots recorded, not papered over

These are properties of the measurement, not of the release. Each one means "the delta is silent
here", which is not the same as "nothing changed".

- **The five `*.Gen` generators have no baseline at all.** `PicoAop.Gen`, `PicoCfg.Gen`,
  `PicoDI.Gen`, `PicoLog.Gen`, `PicoMediator.Gen` are `IsPackable=false`, so the surface tool never
  sees them. They nevertheless **ship to consumers**, embedded as analyzer DLLs inside the `*.Abs`
  package (`PicoAop/src/PicoAop.Abs/PicoAop.Abs.csproj:38`,
  `PicoCfg/src/PicoCfg.Abs/PicoCfg.Abs.csproj:40`). Everything a generator *emits* at a consumer's
  compile time — `CfgBind` members, `Wrap_*` proxies, mediator dispatch — is invisible to any API
  baseline, so a generator change that alters emitted code is undetectable by this rule.
- **`PicoAop`'s baseline is 0 lines.** It is a metapackage; a package-level change (a dependency
  added or dropped) cannot be represented, and the diff for it is `added=0 removed=0` no matter
  what happens to it.
- **Attributes, nullability annotations, generic constraints and mixed `in`/`ref` are ignored.** An
  `[Obsolete]`, a nullable-reference flip or a tightened constraint produces **no delta line** and
  therefore no `x` bump. This release declares none of these — but the tool would not have said so.
- **Behaviour never appears.** Six PicoDI breaking changes and the cron fix ship in this version
  with a byte-identical API surface.

### 2. `AnalyzerReleases.Unshipped.md` does not exist, and should

**Confirmed absent:** `find . -name 'AnalyzerReleases*'` and `git ls-files | grep -i analyzerrelease`

23 IDs, no release tracking, and every one is `isEnabledByDefault: true` (18 `Error`, 5 `Warning`)
— so a consumer build sees them. The tell is that **all five generator projects suppress `RS2008`**
("enable analyzer release tracking") in `NoWarn`: the rule that asks for the very file that is
missing.

**What the file would have to contain** (contents deliberately not invented here — this is the
shape, not a draft):

- `AnalyzerReleases.Unshipped.md` — `### New Rules`, `### Changed Rules`, `### Removed Rules`
  tables with columns `Rule ID | Category | Severity | Notes`, one row per descriptor that is new,
  reworded or retired since the last release; `AnalyzerReleases.Shipped.md` holds the rows promoted
  at a release.
- An `AdditionalFiles` item per generator project pointing at both files, with `RS2008` dropped
  from `NoWarn` — it is suppressed today precisely because no such file exists.
- Because the generators are embedded in `*.Abs`, "shipped" is a property of the **`*.Abs`
  package's** version, not of the generator project — the rows must be promoted on the same tag
  that publishes them.

Its 23 initial rows are a real task: each needs its `Category` and `Severity` read from the
descriptor, and nothing in this release changes a descriptor, so it is a prerequisite for the next
one rather than a blocker for `2026.11.0`.
