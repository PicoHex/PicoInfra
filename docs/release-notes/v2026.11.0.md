## Why this is an `x` bump and not a `y` bump

`2026.10.1` → `2026.11.0`: the public API changed, even though most of the change is additive. The
rule is "API changed", not "API broke" — one added public member bumps `x`, and `y` returns to `0`.
The tool answers this directly:

```text
$ dotnet picohex-api-surface.dll next-version --last v2026.10.1 --api-changed true --year 2026

```

(`api/*.public.txt` at `main` commit `24c72c5`, the release-prep commit that seeds them; the copies I
measured against, taken from `chore/release-prep` at `356d504`, are byte-identical to them):

## Wire and behaviour deltas (surface identical, behaviour is not)

The API diff cannot see any of the items in this section. Each one changes what a consumer
observes, so they are stated here rather than inferred from silence.

### `PicoLog.Json` — the SeqSink wire bytes changed spelling (`994534d`)

`SeqSink` now builds each CLEF batch with the PicoJetson `JsonWriter` instead of the hand-rolled
escaper it carried while it lived in the core package. Same document, same content type
(`application/json; charset=utf-8`), same envelope recreated per retry — but **5 of 12 pinned wire
shapes differ in how a character is spelled**:

- `\b` and `\f` are emitted as `\u0008` and `\u000C` (the writer only uses the short form for the
  three escapes JSON defines: `\n`, `\r`, `\t`);
- hex digits are uppercase (`\u001F`, not `\u001f`);
- an unpaired surrogate reaches the wire as the UTF-8 bytes of U+FFFD (3 bytes) instead of the
  escape text `\ufffd` (6 bytes) — the same substitution the old code chose deliberately.

All 12 shapes decode to the identical document. The corpus itself lives in the commit message of
`994534d` (dumped from the real sink before and after the change — it is not a test
fixture); what the tests pin is the exact CLEF body of a batch (`SeqSinkWireFormatTests`) and the
escape-spelling table (`SeqSinkEscapingTests.Escaping_UsesTheDocumentedForms_Exactly`, which names
``/`` and uppercase hex as the deliberate change). A Seq server sees no semantic difference;
a byte-for-byte snapshot on your side will.

### `PicoCfg` — TOML and YAML are parsed by their format's reader (`edf2cfd`, `79b3283`, `660bb30`)

The two text backends used to carry a hand-written line splitter each. They now read through
`TomlReader` / `YamlReader`, which changes what a *given* document flattens to:

| Document | Before | Now |
|---|---|---|
| `Servers:` + `- a` + `- b` | the sequence vanished (a `- a` line has no `:`) | an array; skipped unless `flattenArrays: true` |
| `Script:` + a block scalar body | `Script` held the indicator character, body vanished | block scalar read as one value |
| `Items:` + `- name: x` | everything vanished | an array of tables |
| `[[servers]]` + `name="alpha"` | key `[servers]:name`, every row but the last silently overwritten | `servers:0:name`, one row per element |
| `ports = [1, 2, 3]` | the literal string `"[1, 2, 3]"` | an array; skipped unless `flattenArrays: true` |
| `[[s]]` … `[z]` after it | `z`'s keys landed under `s:0:` | each key under its own table |
| `host = "h"` + `ports = [1, 2]` | `ports == "h"`, elements at the root as `0`/`1` | `ports:0`, `ports:1` |

A configuration that loaded on `2026.10.1` can therefore resolve to **different values**, or to the
same values under different keys, without any compile error. `PicoCfg.Ini` is deliberately
unchanged (INI has no arrays) and `PicoCfg.Json` was already the counter-example.

These three commits are declared in [`CHANGELOG.md`](../../CHANGELOG.md) too, under *PicoCfg — TOML
and YAML are parsed by their format's reader*, a section added with this release: a behaviour break
of this size belongs beside the six behaviour-only PicoDI entries already there, and a CHANGELOG
kept in step with the API diff alone will keep missing this class of change. The delta cannot see
this one, so the two records are complementary rather than duplicated — the table above is the
before/after, the CHANGELOG section is the migration.

### `PicoCfg` — the collision guard also changes an INI *rule* (`da73005`)

Declared in the CHANGELOG (cross-referenced below, not repeated): `':'` may no longer appear in an
INI section name or key, because INI already nests with `'.'`. This is a new document rejection,
not a new member.

## Limitations left open

Product limitations, unchanged and unhidden:

- **YAML reader gap, compensated nowhere on purpose.** YamlReader delivers the first inline member
  of a sequence item (`- name: x`) as one raw string, and a nested sequence (`- - 1`) as `"- 1"`.
  Splitting those here would put a hand-written YAML parser back in the flattener — the bug that
  was just removed. `YamlNestedStructureTests` pins what the reader actually delivers.
- **TOML inline tables** (`t = { a = 1 }`) still flatten `a`/`b` without the `t` prefix.
- **Nested value arrays** (`m = [[1, 2], [3]]`) still collide at `m:0`.
- **`PicoCfg.Json` is not covered by the collision guard** — it flattens the same way and stays
  last-wins.
- **No `SeqSink` forwarder, no `[Obsolete]` stub** — a forwarder would make `PicoLog.dll` reference
  `PicoLog.Json.dll` and through it the serializer; a stub would keep the JSON-writing code in core.
- **`flattenArrays` prose exists — these notes add the cross-package summary, not the first
  documentation.** `PicoCfg/README.md:84-105` carries a whole **Arrays and Sequences** section
  (added with the API change, `41b5de4`), root `README.md:188` names the flag, and
  [`CHANGELOG.md`](../../CHANGELOG.md) describes the binary break; the four methods also carry XML
  docs and `AddJson` had the flag since `2026.10.1`. What is not written anywhere else is the
  flag's shape across all three text backends in one place — which is what the table above is for.

### Deadlines a starved `ThreadPool` does not honour

`ShutdownTimeout` and `HostedSvcStopTimeout` (the per-hosted-service stop budget behind
`SvcContainer.DisposeAsync`) are enforced by a `CancellationTokenSource` timer, and a timer callback
is `ThreadPool` work: the runtime's timer queue only notices that the deadline passed, a pool thread
runs the cancel, and another resumes the `await` behind it. Under total pool starvation neither
deadline is honoured at all — the wait simply does not end — and a *partially* starved pool stretches
the same budget to an arbitrary length. The audit behind this note derives both halves from CI run
41813752088 (`.github/workflows/ci.yml:464-466`, `windows-latest`, 4 vCPU): a test with a 500 ms
`ShutdownTimeout` was still waiting on `DisposeAsync` roughly 20x its budget later, when its own
ten-second deadline fired, while the four other legs passed the same suite; and a fully occupied pool
does not even produce that `TimeoutException`, because the test's own timer needs a pool thread too.
The honest statement of the limit is therefore that these deadlines degrade from "the budget" to
"whenever a worker frees up" — while the documentation, when the audit ran, promised the budget
itself (`PicoLog/README.md:374-383` told a caller to set `ShutdownTimeout` to bound the drain, and
`SvcContainer.Hosting.cs:545-560` said the wait itself ends at the deadline). This release withdraws
that promise from the description, and only from the description: the packed readme
(`PicoLog/README.md`, `## Flush & Shutdown`, caveat at `:383-387`), the private method's `<remarks>`
(`RunPhaseWithinDeadlineAsync`, `SvcContainer.Hosting.cs:552-556`) and `ShutdownTimeout`'s XML doc
(`LoggerFactoryOptions.cs:30-35`) now each say the pool can refuse the timely cancel. Not one
statement changed — comments and Markdown only — so everything measured below stands as recorded.

**Scope as measured: 10 timer-backed deadlines in `src/`.** Six are shutdown deadlines, and those
are the ones a consumer can hit:

| file:line | deadline it does not enforce |
|---|---|
| `PicoDI/src/PicoDI/SvcContainer.Hosting.cs:443` (enforced at `:586`, `WaitAsync(deadline)` in `RunPhaseWithinDeadlineAsync`) | the per-hosted-service stop budget, used by `SvcContainer.DisposeAsync` and by the failed-start rollback |
| `PicoLog/src/PicoLog/CategoryPipeline.cs:132` | the drain budget of `LoggerFactory.DisposeAsync` — default **30 s** (`LoggerFactoryOptions.cs:36`), the only one of the six a caller can act on, and `TimeSpan.Zero` means unbounded because the guard at `:131-133` then creates no timer at all; its cancel reaches the in-flight sink write at `InternalLogSinkDispatcher.cs:144` |
| `PicoSchedule/src/PicoSchedule/Scheduler.cs:141` | how long `Scheduler.StopAsync()` waits for the tick loop to join |
| `PicoSchedule/src/PicoSchedule/Scheduler.cs:160` | how long `StopAsync()` waits for in-flight sink calls before abandoning them |
| `PicoCfg/src/PicoCfg/CfgRoot.cs:113` | how long `CfgRoot.DisposeAsync` waits for an in-flight reload to release `_reloadGate` |
| `PicoCfg/src/PicoCfg/CfgRoot.cs:154` | the secondary drain attempt of that same gate |

The other four are scheduled ticks (`SeqSink`'s 2 s flush, `Scheduler`'s 10 s tick,
`FileWatchingCfg`'s 2 s watcher retry and its 200 ms debounce). A late tick self-heals, so none of
them is proposed for the fix — but one carries a consequence of its own: the `SeqSink` buffer is
bounded only *reactively*. `PicoLog/src/PicoLog.Json/SeqSink.cs:192-193` starts a drain when
`MaxBatchEntries` / `MaxBatchBytes` are reached, and those are trigger thresholds, not caps: the
only appender, `BufferEntries` (`SeqSink.cs:173`), never drops and never refuses, so a stalled flush
tick lets `_buffer` grow without bound — memory growth, and every entry in it is lost if the process
exits.

There is **no shared timeout helper**: each site hand-rolls one of five spellings
(`new CancellationTokenSource(timeout)`, `WaitAsync(TimeSpan)`,
`SemaphoreSlim.WaitAsync(TimeSpan, ct)`, `PeriodicTimer`, `Task.Delay`), so there is no single place
that ever made the pool-independence decision. Three shapes in the tree are already pool-free and
must **not** be unified onto a timer — `FlushQuiesceCoordinator` (a `Stopwatch` deadline waited on
by the calling thread), `InternalLoggerQueue` (an OS sleep in a `Stopwatch`-bounded backoff loop) and
`FileSink` (a `TryRead` with no timer at all). They are the templates for the fix, not candidates
for it.

**Intended direction, deliberately out of scope for this release:** one internal deadline helper —
the safe blocking shape where a caller's thread is available, plus a lazily created dedicated
watchdog thread that performs the escalation where it is not — applied to the six shutdown call
sites above, and a hard cap on `SeqSink`'s `_buffer` (drop-oldest, the policy the pipeline queue
already has). That is one new internal type, six call sites and one `if`, across PicoDI, PicoLog,
PicoCfg and PicoSchedule; it needs its own measurement and review, so `2026.11.0` records the
limitation instead of carrying a late fix for it.

### Tool blind spots recorded, not papered over

These are properties of the measurement, not of the release. Each one means "the delta is silent
here", which is not the same as "nothing changed".

- **The five `*.Gen` generators have no baseline at all.** `PicoAop.Gen`, `PicoCfg.Gen`,
  `PicoDI.Gen`, `PicoLog.Gen`, `PicoMediator.Gen` are `IsPackable=false`, so the surface tool never
  sees them. They nevertheless **ship to consumers**, embedded as analyzer DLLs inside the `*.Abs`
  package (`PicoAop/src/PicoAop.Abs/PicoAop.Abs.csproj:38`,
  `PicoCfg/src/PicoCfg.Abs/PicoCfg.Abs.csproj:40`). Everything a generator *emits* at a consumer's
  compile time — `CfgBind` members, `Wrap_*` proxies, mediator dispatch — is invisible to any API
  baseline, so a generator change that alters emitted code is undetectable by this rule.
- **`PicoAop`'s baseline is 0 lines.** It is a metapackage; a package-level change (a dependency
  added or dropped) cannot be represented, and the diff for it is `added=0 removed=0` no matter
  what happens to it.
- **Attributes, nullability annotations, generic constraints and mixed `in`/`ref` are ignored.** An
  `[Obsolete]`, a nullable-reference flip or a tightened constraint produces **no delta line** and
  therefore no `x` bump. This release declares none of these — but the tool would not have said so.
- **Behaviour never appears.** Six PicoDI breaking changes and the cron fix ship in this version
  with a byte-identical API surface.

### 2. `AnalyzerReleases.Unshipped.md` does not exist, and should

**Confirmed absent:** `find . -name 'AnalyzerReleases*'` and `git ls-files | grep -i analyzerrelease`
both return nothing. No `*.Gen` csproj declares an `AdditionalFiles` item for one.

**Why that is a gap, not a style choice:** this repository ships source generators, so its
diagnostics are consumer-facing even though the generator projects are not packable. The analyzers
are embedded in the `*.Abs` packages and their IDs are hit by real consumer builds:

| Generator | Descriptors (measured in source) |
|---|---|
| `PicoAop.Gen` | 7 — `PICO101`, `PICO102`, `PICO105`, `PICO110`, `PICO111`, `PICO112`, **`PICO113`** (`PicoAopDiag.cs`) |
| `PicoCfg.Gen` | 10 — `PCFGGEN001`…`PCFGGEN010` (`PicoCfgBindGenerator.Diagnostics.cs`) |
| `PicoDI.Gen` | 5 — `PICO002`…`PICO006` (`DiagnosticDescriptors.cs`) |
| `PicoMediator.Gen` | 1 — `PMGEN001` (`MediatorGenerator.cs`) |
| `PicoLog.Gen` | 0 |

23 IDs, no release tracking, and every one is `isEnabledByDefault: true` (18 `Error`, 5 `Warning`)
— so a consumer build sees them. The tell is that **all five generator projects suppress `RS2008`**
("enable analyzer release tracking") in `NoWarn`: the rule that asks for the very file that is
missing.

**What the file would have to contain** (contents deliberately not invented here — this is the
shape, not a draft):

- `AnalyzerReleases.Unshipped.md` — `### New Rules`, `### Changed Rules`, `### Removed Rules`
  tables with columns `Rule ID | Category | Severity | Notes`, one row per descriptor that is new,
  reworded or retired since the last release; `AnalyzerReleases.Shipped.md` holds the rows promoted
  at a release.
- An `AdditionalFiles` item per generator project pointing at both files, with `RS2008` dropped
  from `NoWarn` — it is suppressed today precisely because no such file exists.
- Because the generators are embedded in `*.Abs`, "shipped" is a property of the **`*.Abs`
  package's** version, not of the generator project — the rows must be promoted on the same tag
  that publishes them.

Its 23 initial rows are a real task: each needs its `Category` and `Severity` read from the
descriptor, and nothing in this release changes a descriptor, so it is a prerequisite for the next
one rather than a blocker for `2026.11.0`.

  `Json` / `Yaml` / `Ini` / `Toml`, which exist under `PicoCfg/src/`; and root `README.md`'s module
